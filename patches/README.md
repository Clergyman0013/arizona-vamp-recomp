# Toolkit patches

`tools/xboxrecomp` is a clone of upstream
[sp00nznet/xboxrecomp](https://github.com/sp00nznet/xboxrecomp). The fixes this
port needs live in `xboxrecomp-darkwatch.patch` against release **v0.14.0**
(commit eb0aa1d).

Apply to a fresh clone:

```bash
git clone https://github.com/sp00nznet/xboxrecomp tools/xboxrecomp
git -C tools/xboxrecomp checkout v0.14.0
git -C tools/xboxrecomp apply ../../patches/xboxrecomp-darkwatch.patch
```

`wip-xboxrecomp-preemption.diff` is parked, unreviewed work against the older
v0.13.1 base; it is not part of the patch and does not apply to v0.14.0.

### Rebased onto v0.14.0 (2026-10-16)

v0.14.0 took several of these fixes upstream in its own form, and changed
code around others. On the rebase:

| Area | Now | Why |
|---|---|---|
| POSIX partition images, NtClose dropping a directory search, `FileAllocationInformation` on POSIX, arm64 MMIO decode for APU/AC'97/OHCI | **upstream's** (v0.14.0's macOS/Linux and kernel PRs); ours removed, including `src/apu/apu_mmio_hook_arm64.c`, and Darkwatch's crash handler now calls upstream's `xbox_PosixMmioFault` | the same fixes, maintained there |
| Contiguous allocator | upstream's page allocator (#189), plus a floor: blocks start above the loaded image when the range allows | upstream's allocator hands out pages from the bottom, so blocks aliased image addresses; Darkwatch's XPP keeps USB descriptors in both, the OHCI model could not tell them apart, and the gamepad never finished enumerating (the boot sat on the CAPCOM logo) |
| `xbox_PhysIsContiguous` | answered from upstream's page map | the bump-pointer bounds it used are gone |
| DSP boot ROM (`apu_dsp.c`) | the memory layout registers where the GP/EP windows are (`mcpx_apu_dsp_set_windows`); the reset registers are polled there | v0.14.0 traps only APU 0x00000-0x2FFFF and leaves GP/EP as RAM; tests that build the APU alone have no such memory and no longer touch it |
| AC'97 write trap (macOS) | stores are emulated through a writable `mach_vm_remap` alias of the page; the trapped page is never opened | opening it to emulate one store let another thread's store land untrapped; DirectSound, which reads the register once after writing RR and spins on that value, froze in Darkwatch's attract demo. Linux arm64 keeps upstream's open-window path |
| Fixed function | upstream's composite-matrix path stays the default; `RECOMP_FF_TNL=1` takes our transform-and-lighting unit (`nv2a_ff.c`), and it sees every subchannel-0 method first | the two light upstream's two-light test case differently; Darkwatch's level, 77% fixed function, was brought up through the unit, and `darkwatch/src/config.c` sets the switch |
| Imm-ref pass | upstream's closed-CFG proofs, plus our this-adjust thunk, after-padding and gap-`ret` acceptances | upstream's rewrite dropped them; Darkwatch's MPEG decoder callback and switch-dispatch callbacks need them |
| Data-pointer pass | upstream's proofs, plus: a target right after a decoded `ret` or unconditional `jmp` is accepted if its stream reaches one | delegate and adjusting vtable thunks end in an indirect `jmp` no proof can close; Darkwatch's front end calls 0x000EF6C1, 0x001D37AC and 0x001F2AD9 at boot |
| Thread creation | upstream's guest thread objects and TLS, with our guest-CPU token and `CREATE_SUSPENDED` slots threaded through | both are needed: upstream's for TLS, ours for CRI's suspended workers |
| SDL window (`fb_present_sdl.c`) | the guest pthread takes the guest-CPU token first; `main` gives it up before starting the guest, and takes it back if the start fails | `main` held the token from start-up, so the guest's first `PsCreateSystemThreadEx` waited on it forever. Darkwatch's `main_posix.c` now enters through `xbox_HostWindowMain` |

Function detection on v0.14.0 takes about 9 minutes for Darkwatch (about 30 s
before): the closed-CFG proofs. It finds 34,676 starts where v0.13.1 + this
patch found 36,369; the difference is mostly junk starts the new rules reject.

Checked: every toolkit test that passes on pristine v0.14.0 on this Mac passes
with the patch (34 C test projects, 804 Python tests); the rest fail to build
or configure on pristine v0.14.0 here too. Darkwatch boots, plays its attract
demo, and goes through the menus and briefing into the first level, as on
v0.13.1. Not checked: a Windows build.

except the comments that say where each problem was found.

## XboxXBERecomp (the HLE port in `darkwatch-hle/`)

`third_party/XboxXBERecomp` is a clone of upstream
[TGP482/XboxXBERecomp](https://github.com/TGP482/XboxXBERecomp) (MIT) at commit
99078b1 (its `main`, 2026-10-18). The changes this port needed are in `xboxxberecomp-darkwatch.patch`:

```bash
git clone https://github.com/TGP482/XboxXBERecomp third_party/XboxXBERecomp
git -C third_party/XboxXBERecomp checkout 99078b1
git -C third_party/XboxXBERecomp apply ../../patches/xboxxberecomp-darkwatch.patch
```

compiles" in b47e2e9 and reverted it in 3010abc a minute later, while 99078b1's `release.bat` and README still
describe it. The patch puts b47e2e9 back in full (this is what lets a release ship the compiler instead of the game
code), then the Darkwatch changes below. Merges on the way:
